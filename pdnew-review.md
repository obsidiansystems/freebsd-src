# Code review: `main..better-proc-spawn` (pdnew family)

Reviewed against each commit's own parent. Line numbers are from the worktree (`sys/kern/sys_pdnew.c` etc.). Four blockers, one hang, and a cluster of security/lifetime regressions land in the feature commit; the two "NFC" refactors both violate their claims (one benignly, one with a real arm panic).

**Finding status:** ✅ fixed · 🟡 open · 📌 accepted (benign, documented, kept out of the NFC commits)

## Status (updated after the NFC-separation pass, 2026-07-23)

The commits were reorganized after this review, so the SHAs in the section headers below are **stale**. Current stack: priv-lift → `do_execve` factor (NFC) → `do_fork` factor (NFC) → `fork1` allocation factor (non-NFC, documented) → feature → tests.

### ✅ Fixed / resolved — the commit-hygiene program (§1, §2)
- **§1 priv-lift arm panic** — `proc_writemem()` now uses `priv_check(curthread, …)`. **FIXED.**
- **§2 factor deltas** — the factor commit was split into a provably-NFC `do_execve` commit, an NFC `do_fork` commit, and one clearly-labeled non-NFC `fork1` commit:
  - `euipp` leak — **FIXED** (helper no longer resets `*euipp`).
  - double `pause` — **FIXED** (removed from `fork_alloc_proc`).
  - setid-before-fd-safety — **FIXED** (un-bundled; `do_execve` restored to the original order).
  - nprocs/`chgproccnt` reorder — **ISOLATED** into its own non-NFC commit, documented as a deliberate benign reorder (shared allocation path ⇒ free test coverage for `pdnew`).

### ✅ Fixed — feature memory-safety blockers (§3)
All fixed and **validated on amd64**: pdnew 9/9 + regression 102/103 (same one pre-existing unrelated ptrace failure), no panic, across two build+boot cycles.
- **pdstart lost `P_INEXEC_WAIT` wakeup** (unkillable hang) — FIXED: pdstart now does `wakeup(&p->p_execblock)` + clears `P_INEXEC_WAIT`, mirroring `do_execve`.
- **`proc_destroy_embryonic` missing `callout_drain(&p_limco)`** — FIXED (+ `pargs_drop(p->p_args)`, with the embryo's `p_args` NULLed until `exec_finalize` installs an owned copy).
- **pdsetfd UAF** — FIXED: `procdesc_find` now returns the procdesc *file* reference held; callers `fdrop` it after use, keeping the embryo alive against a racing `close(2)` (cleaner than `_PHOLD` — no destroy runs while a ref is held).
- **Phase-3 UAF / double-free** — FIXED: `fp_procdesc` is now held across all of Phase 3 (the `fdrop` moved to the end paths), so a racing `close` cannot free `p2` mid-construction.
- **`td_startcopy` uninitialized** (was §3 High) — FIXED: `kern_pdnew` bcopies `td_startcopy` from the caller, byte-exact with `do_fork`.
- **Capsicum rights amplification in pdsetfd** (was §3 High) — FIXED: `fget_cap` captures the source fd's rights and installs them, instead of `NULL` → `CAP_ALL`.
- **i386/arm `cpu_fork` panic** — FIXED; **amd64 mechanics validated, needs an i386/arm boot to confirm**: `cpu_fork` moved after exec creates the vmspace, so it no longer derefs a NULL `p_vmspace` (reorders it after `process_fork`, which no in-tree handler cares about).

### ✅ Also fixed (batch 3, validated on amd64: pdnew 9/9 + regression 102/103, no panic)
- **32-bit ABI wrong-address-space** — FIXED: `freebsd32_copyout_strings` and `linux_copyout_strings` (amd64 linux32) migrated to `imgp_copyout`/`imgp_suword32`, plus the shared `__linuxN(copyout_auxargs)` to `imgp_copyout`, so a 32-bit binary via `pdnew` writes the child's AS, not the caller's. (Native-64-bit-linux `__linuxN(copyout_strings)` left as-is — separate ABI, same mechanical fix if wanted.)
- **`exec_map_stack` targeted the caller** — FIXED: uses `kern_proc_setrlimit(p, ...)` on the embryo (which is `P_INEXEC`), not `kern_setrlimit(curthread, ...)`.
- **interpreter-loop leaks** — FIXED: frees the previous iteration's `newtextdvp`/`newbinname`/namei pnbuf, mirroring `do_execve` (guarded on `args->fname`; `fname` reset on the `interpreter_vp` path).
- **shebang `/dev/fd/N` install** — FIXED: `fget_cap` preserves the exec fd's rights (same amplification fix as pdsetfd).

### ✅ Also fixed
- **`CAP_PDKILL` confused deputy** (§3 high) — FIXED: a new `CAP_PDSETFD` capability right now gates `pdsetfd` (mirroring `pddupfd`/`CAP_PDDUPFD`); `pdstart` keeps `CAP_PDKILL` since `pdnew` already gates exec via `CAP_FEXECVE`. So a delegated procdesc can permit start/kill without permitting fd injection. Documented in `rights(4)` + `pdfork.2` (incl. a `SECURITY CONSIDERATIONS` section). Builds; **boot test pending**.

### ✅ Also fixed
- **set-uid stdio** (§3 high) — FIXED by design: dropped the `fdcheckstd`/`/dev/null` half (pdnew doesn't enforce the stdio convention — the caller populates 0/1/2 via `pdsetfd` if it wants them). Kept the `fdsetugidsafety` protection at the `pdsetfd` chokepoint: refuses (`EPERM`) an unsafe (`VV_PROCDEP`) descriptor at fd 0/1/2 when installation is *restricted* — a `P_SUGID` embryo (set-uid **or** set-gid), or an injector whose `cr_uid`/`cr_gid` differs from the embryo's creator — unless the *embryo* runs in capability mode (the delegated-procdesc confused-deputy case exec has no analog for). Guards exactly 0/1/2 per libc's stdio contract (mirroring execve; fd ≥ 3 unsafe is already permitted). `is_unsafe` → exposed as `fdesc_is_unsafe`. Documented in `pdfork.2`. Builds; **boot test pending**.

### ✅ Also fixed
- **`process_fork`/`process_exit` pairing** (§3 medium) — FIXED by deferring observation: `process_fork` (+ the `proc:::create` probe) is no longer fired in `pdnew`; it fires in `pdstart` once the embryo commits to running, keyed on the embryo's `p_pptr` (the pdnew creator, not the possibly-delegated pdstart caller; `PHOLD` pins it across the invoke). A cancelled embryo therefore never appears to fork/exit handlers, so the balance is correct **by construction** — `proc_destroy_embryonic` needs no `process_exit`, and the full exit-handler chain never runs on a never-ran proc. Only filemon + hwpmc register `process_fork` (the two that were leaking); the other five `process_exit` handlers pair no fork and are unaffected.

### ✅ Also fixed — completeness nits (rlimit edges)
- **`finstall_at` EMFILE keyed to the caller** — FIXED: `finstall_at` bounded `atfd` by `getmaxfd(td)` (the pdsetfd *caller's* `RLIMIT_NOFILE`) while installing into the *embryo's* fd table. Its `fdp` param is now the owning `struct proc *p`; it bounds `atfd` by `lim_cur_proc(p, RLIMIT_NOFILE)` (the embryo's limit) and derives `fdp = p->p_fd`. `td` is still used to close any replaced descriptor. Both pdnew call sites updated; `finstall_at` is feature-new so no other callers.
- **`exec_map_stack` ASLR data reservation keyed on `curthread`** — FIXED: the ASLR stack and shared-page addresses were placed at `vm_daddr + lim_max(curthread, RLIMIT_DATA)` — the caller's DATA limit, not the embryo's. If the caller's `RLIMIT_DATA` max were smaller than the embryo's, the embryo's data segment could later grow into the stack. Now `lim_max(imgp->td, RLIMIT_DATA)` (`imgp->td == td2`, the embryo thread), matching `imgact_elf.c`'s own daddr+DATA math. (`exec_new_vmspace` was already clean — it uses `imgp->proc` and skips the curproc-assuming handlers for embryos.)

### 📌 Accepted by design (not fixed)
- **`process_exec` / `proc:::exec` not fired for embryos** — intentional, not an oversight: `exec_new_vmspace` (`kern_exec.c:1516-1521`) deliberately guards `EVENTHANDLER_DIRECT_INVOKE(process_exec)` behind `vmspace != NULL`, which is false for an embryo, precisely because those handlers assume `curproc` (e.g. aio rundown) and the embryo is not `curproc`. Path B reinforces this: `process_fork` now fires only at `pdstart`, so firing `process_exec` during `pdnew` (the only time `imgp` is alive) would be exec-before-fork and filemon would drop it anyway. Net effect: filemon/audit don't record the binary a pdnew'd process runs. A proper fix would need to stash exec metadata and synthesize the event at `pdstart` — a separate feature, not a correctness gap.

## 1. `00192f9cbba5` — lift priv check out of `vmspace_rwmem()` *(claims NFC)*

**✅ FIXED.** **Verdict (original): NFC claim NOT upheld — introduces a userspace-reachable panic on arm.** The read/write `reqprot` split and the priv relocation are faithful for every `curthread` caller, but the subject change breaks the one non-`curthread` caller.

- ✅ **[high]** `sys/kern/sys_process.c:~595` — `proc_writemem()` now calls `priv_check(td, PRIV_PROC_MEM_WRITE)` on the *passed* `td` instead of `curthread`. `priv_check()` opens with `KASSERT(td == curthread)`. On arm, `ptrace_write_int()` (`sys/arm/arm/machdep_ptrace.c:51`) calls `proc_writemem(td, td->td_proc, …)` where `td` is the **traced target thread** (`td2`, selected in `kern_ptrace` for PT_STEP/PT_SETSTEP/PT_CLEARSTEP), not the debugger. Failure: an unprivileged user single-steps their own child on an INVARIANTS arm kernel (arm GENERIC default) → `ptrace(PT_STEP)` → `proc_writemem(td2,…)` → KASSERT fires → **kernel panic**. On non-INVARIANTS kernels it silently evaluates the target's cred instead of the debugger's (wrong under MAC/veriexec). Correctly identified NFC violation and vulnerable caller; note the candidate's `EPERM→ENOMEM` symptom is *wrong* — `PRIV_PROC_MEM_WRITE` is granted to every cred (`kern_priv.c:247`), so the real symptom is the KASSERT panic, not EPERM. `proc_rwmem` keeps `td=curthread`; dtrace/PT_WRITE callers unaffected.

**✅ FIXED** — `proc_writemem()` now uses `priv_check(curthread, …)`; `td` stays as the fault context passed to `vmspace_iop()`. (TODO: final boot-test confirm on arm + INVARIANTS.)

## 2. `e64cbd8a8cd8` — factor `fork1()`/`do_execve()` into helpers *(claims pure NFC)*

**✅ RESOLVED** — all four deltas fixed or isolated (see Status); the commit was split into a provably-NFC `do_execve` commit, an NFC `do_fork` commit, and one labeled non-NFC `fork1` commit. **Verdict (original): NOT strictly NFC — four real but benign behavior deltas on error/interpreter paths; no memory-safety defect, locking/vnode-lock states preserved.**

- 📌 **[low]** `sys/kern/kern_exec.c:481` — `exec_activate()` unconditionally does `*euipp = NULL` on entry, dropping the `uidinfo` ref that the inline code carried across the shebang re-entry loop. Exec a setuid `#!` script whose interpreter is not itself set-id: iter1 sets `euip=uifind(script_owner)`; iter2's `*euipp=NULL` overwrites it with no `uifree()` → one leaked `uidinfo` ref per such exec. Parent kept `euip` as a persistent local freed once at the end.
- 📌 **[low]** `sys/kern/kern_fork.c:475` + `1250` — `fork_alloc_proc()` fail paths `pause("fork", hz/2)`, then `fork1()` cleanup pauses again. A `fork_alloc_proc`-origin failure (RLIMIT_NPROC/maxproc EAGAIN, `thread_alloc` ENOMEM, racct) now sleeps ~1s instead of ~0.5s, and inconsistently vs `vmspace_fork`/`procdesc_falloc` failures which still pause once.
- 📌 **[low]** `sys/kern/kern_exec.c:1239` vs `1245-1268` — `exec_install_setid()` (`proc_set_cred` + `mac_vnode_execve_transition`) now runs **before** `fdsetugidsafety()`/`fdcheckstd()`; the original ran the cred install after. On the `fdcheckstd`-failure path (setuid binary, fds 0-2 closed, ENFILE/EMFILE) the process is killed and accounted under the **new** set-id cred with the MAC transition already applied. Refcounts stay balanced (`oldcred` NULLed → `exec_cleanup_cred` no-op) and `fdcheckstd` uses `td_ucred`, so **no escalation**; one lens further notes acct uses `cr_ruid` (unchanged), so the only observable delta is `wait()` `si_uid`/MAC exit labels on a doomed process. Benign ordering delta, but contradicts NFC.
- 📌 **[low]** `sys/kern/kern_fork.c:~1194` — folding the nprocs/maxproc check + `chgproccnt` into `fork_alloc_proc` (run before `vmspace_fork`/`swap_reserve`) flips the errno winner under simultaneous exhaustion (EAGAIN now beats ENOMEM), and the maxproc path now transiently single-threads the caller + churns a procdesc fd before failing. Cleanup is correct (`proc_unset_cred(newproc, true)` balances the early `chgproccnt`); both errnos are valid POSIX. Behavior delta under NFC claim.

## 3. `118d6469720d` — Add `pdnew`, `pdsetfd`, `pdstart` *(the feature)*

**🔴 OPEN — fix now.** **Verdict: NOT ship-ready.** Four independent userspace-reachable memory-safety blockers, a lost-wakeup hang, and a cluster of security/lifetime regressions. The root cause is uniform: the procdesc is made **closeable while the proc is still an unreferenced, half-built embryo**, and `proc_destroy_embryonic()` is not a faithful mirror of `exit1()`.

### Blockers

- ✅ **[blocker]** `sys/kern/sys_pdnew.c:285` (`cpu_fork`), `p_vmspace=NULL` @`251` — `cpu_fork(td, p2, td2, RFPROC)` runs with `p2->p_vmspace == NULL` (vmspace is only created later inside `exec_activate`). i386 `cpu_fork` does `pcb2->pcb_cr3 = pmap_get_cr3(vmspace_pmap(p2->p_vmspace))` (`vm_machdep.c:263`); arm does `pmap_set_pcb_pagedir(vmspace_pmap(NULL), pcb2)` (`vm_machdep.c:124`). `vmspace_pmap(NULL)` is a near-NULL pointer that is then dereferenced → **guaranteed kernel panic on every `pdnew(2)`** on i386/arm. Invisible on amd64/arm64 (their `cpu_fork` never touches `p_vmspace`). Fix: create the vmspace before `cpu_fork`, or add an embryonic `cpu_fork` variant that only builds the trampoline.

- ✅ **[blocker]** `sys/kern/sys_pdnew.c:472-496` — **pdsetfd use-after-free.** `procdesc_find()` (`:94`) returns the embryo `p` `PROC_LOCK`ed but `fdrop()`s the procdesc (`:104`) and takes **no `_PHOLD`** — no reference on `p`. `sys_pdsetfd` `PROC_UNLOCK(p)` @`482`, then `finstall_at(td, p->p_fd, fp, …)` @`495` holding nothing. A sibling thread sharing the fd table calling `close(procfd)` is the last ref → `procdesc_close` embryonic branch → `proc_destroy_embryonic(p)` `fdescfree()`s `p->p_fd` and frees `p` to `proc_zone`. `finstall_at` then `FILEDESC_XLOCK`s/writes freed memory → UAF/corruption from **unprivileged** userspace. The mirror `kern_pddupfd` holds `_PHOLD(p)` across the identical window; `procdesc_find` does not (its comment wrongly assumes the embryo "cannot exit"). Same missing-hold pattern also at `:349-356`. *(pdstart @`536` is not a free-UAF: it commits `PRS_NORMAL` + clears `P_INEXEC` under `PROC_LOCK` @`525/528` before unlocking, so a racing close no longer matches the embryonic-destroy branch.)*

- ✅ **[blocker]** `sys/kern/sys_pdnew.c:293-294` — **Phase-3 UAF / double-free.** `procdesc_finit()` + `fdrop()` publish a closeable procdesc into the caller's (predictable lowest-free) fd while `p2` is still `PRS_NEW|P_INEXEC`, then Phase 3 keeps building `p2` with **no lock and no reference**, sleeping on vnode I/O and page faults: `exec_activate` @`318` and `exec_copyout_stack` @`372` fault the image/stack into `p2->p_vmspace` via `imgp_writemem`. A sibling `close(fd)` during that window → `proc_destroy_embryonic(p2)` → `vmspace_free(p2->p_vmspace)` + free `p2` **while Phase 3 is still faulting into that vmspace** → double-free + UAF, then `exec_finalize` on freed memory. `do_fork` avoids this by `finit`'ing only after `p2` is `PRS_NORMAL` and fully built.

- ✅ **[blocker]** `sys/kern/kern_fork.c:1446` — **`proc_destroy_embryonic()` drains `p_itcallout` but never `p_limco`.** `lim_fork(p1,p2)` (`sys_pdnew.c:255`) arms `p2->p_limco` (`callout_reset_sbt(…, lim_cb, p2)`) whenever the parent has a finite `RLIMIT_CPU`. Unprivileged repro: `setrlimit(RLIMIT_CPU, finite)`; `pdnew()`; `close(procfd)` before `pdstart` (or let exec fail) → `proc_destroy_embryonic(p2)` frees `p2` to `proc_zone` with the callout still armed (`p_cpulimit` is in `p_startcopy`, so the embryo inherits the finite value and `lim_cb` re-arms). ~1s later the callout fires on recycled proc memory, locks `p_mtx`, runs `lim_cb` (may `killproc`/re-arm) → UAF/panic/wrong-process kill. `exit1()` drains it (`kern_exit.c:371`); the embryonic path doesn't. Note the drained `p_itcallout` isn't even armed on this path — the wrong callout is drained.

### High

- ✅ **[high]** `sys/kern/sys_pdnew.c:525` — **pdstart drops the `P_INEXEC` wakeup.** It clears the flag with a bare `p->p_flag &= ~P_INEXEC` and omits the `if (P_INEXEC_WAIT) wakeup(&p->p_execblock)` that `do_execve` performs. A concurrent `kern_pddupfd(procfd)` on the embryo (checks only `P_WEXIT`, not `PRS_NEW`) parks uninterruptibly in `execve_block` (`msleep` `PDROP`, no `PCATCH`) on `&p->p_execblock`; nothing on the pdstart/run path ever wakes it → **deterministic unkillable hang**, leaking the `_PHOLD`; if the embryo later exits, `exit1`'s `p_lock` wait deadlocks the pair. Reachable via `pdnew` + `pddupfd`(second thread) + `pdstart`, all CAPENABLED. *The candidate's UAF escalation is refuted:* the parked `pddupfd` holds a `struct file` ref on the procdesc, so `close` cannot run `proc_destroy_embryonic` while it sleeps — impact is hang/deadlock, not corruption.

- ✅ **[high]** `sys/compat/freebsd32/freebsd32_misc.c:~3667` — **compat ABI writes the child's stack into the CALLER.** The commit migrated native `exec_copyout_strings` and the shared `__elfN` paths to `imgp_copyout`/`imgp_suword32`, but left `freebsd32_copyout_strings` (and linux32) on raw `copyout()`/`suword32()`, which target `curproc`. (Confirmed: `freebsd32_misc.c` is not in the stack's diffstat.) `exec_copyout_stack` (`sys_pdnew.c:372`) dispatches `sv_copyout_strings` with `imgp->proc = p2 != curproc`, so `pdnew()` of a 32-bit ELF writes argv/env/ps_strings/canary/sigcode into the **parent**. The 32-bit `ps_strings` address is normally unmapped in the 64-bit parent → `copyout` EFAULT → `pdnew` fails for every 32-bit binary; if mapped writable, silent parent corruption + child runs with an uninitialized stack. auxv/argc reach the child correctly (migrated `__elfN` path) — a concrete inconsistency.

- ✅ **[high]** `sys/kern/sys_pdnew.c:485-495` — **Capsicum rights amplification.** pdsetfd fetches the source fd via `fget(td, parent_fd, cap_rights_init(&rights)/*empty*/, &fp)` (succeeds for any restricted capability, discards its filecaps), then `finstall_at(…, fcaps=NULL)` → `_finstall` → `filecaps_fill()` grants `CAP_ALL`/`CAP_FCNTL_ALL`/all-ioctls. All three syscalls are `STD|CAPENABLED`, so a sandboxed process holding a `CAP_READ`-only descriptor can `pdnew`+`pdsetfd` it into the child with **full** rights on the same object → confinement escape / monotonicity violation. The mirror `pddupfd` preserves rights via `fget_remote`+`filecaps_copy`. Same pattern at `:349-354`.

- ✅ **[high]** `sys/kern/sys_pdnew.c:384-390` — **set-uid exec without `fdsetugidsafety()`/`fdcheckstd()`.** `exec_install_setid()` installs elevated creds for a set-id binary, but kern_pdnew never runs the fd-safety block `do_execve` runs at `kern_exec.c:1245-1268`. The embryo's fd table is fresh/empty, so 0/1/2 start **closed** → classic set-uid stdio-descriptor confusion: a root binary's later `open()` returns fd 0/1/2 and it writes secrets to what it treats as stderr. Worsened by pdsetfd (needs only `CAP_PDKILL`) being able to point 0/1/2 at attacker-chosen (incl. `VV_PROCDEP`) objects before `pdstart`. **→ Resolved by design:** the `/dev/null`-filling half (`fdcheckstd`) is intentionally *not* ported — pdnew builds the fd table explicitly via `pdsetfd`, does not enforce the stdio convention, and an empty table is a feature (the caller installs what it wants). The `fdsetugidsafety` half *is* honored, at the natural chokepoint: `sys_pdsetfd` now refuses (`EPERM`) to install an unsafe (`fdesc_is_unsafe`, i.e. `VV_PROCDEP`) descriptor at fd 0/1/2 when installation is *restricted*. Restricted = `P_SUGID` (set-id embryo — faithful `execve` mirror, covers set-uid **and** set-gid) **or** the injector's `cr_uid`/`cr_gid` differs from the embryo's creator (the delegated-procdesc confused-deputy case that has no `execve` analog, since exec has a single principal). The cred-divergence half is skipped when the **embryo** runs in capability mode — a sandboxed process draws authority from its fds, not its ambient uid/gid, so `CAP_PDSETFD` + preserved filecaps are the boundary. It's the *embryo's* capmode that matters, not the caller's: the check protects the embryo, so testing `IN_CAPABILITY_MODE(td)` (the caller) was a bug — fixed to test the embryo's cred (`p->p_ucred->cr_flags & CRED_FLAG_CAPMODE`). Guards exactly 0/1/2 (not fd ≥ 3) because that distinction is a property of libc's stdio contract, not of the spawn mechanism. (`is_unsafe` exposed as `fdesc_is_unsafe` in `filedesc.h`; no logic duplicated. `p_candebug` deliberately *not* used — it keys on the caller's own privilege, the wrong direction.)

- ✅ **[high]** `sys/kern/sys_pdnew.c:228-237` — **`td2`'s `td_startcopy` region is never initialized.** kern_pdnew does `bzero(td_startzero)` + `sched_fork` but omits the `bcopy(&td->td_startcopy, &td2->td_startcopy, __rangeof(td_startcopy, td_endcopy))` that `do_fork` does. `td_sigmask`, robust-mutex heads (`td_rb_list`/`td_rbp_list`/`td_rb_inact`) and sched fields (`td_base_pri`/`td_pri_class`/`td_user_pri`) stay **stale** from the recycled thread; exec can't fix them (`exec_new_vmspace` skips `umtx_exec` when `p_vmspace==NULL`; `execsigs` preserves `td_sigmask`). Consequences: the new program starts with an arbitrary blocked-signal mask (+ sigset info leak); a stale `td_rb_list` from a prior robust-mutex thread → at the new proc's exit `umtx_thread_cleanup` walks that VA in the **new** vmspace and writes `OWNER_DIED` bits at unrelated addresses → silent userspace corruption; a bogus priority is possible via ULE's `td_pri_class` early-return.

- ✅ **[high]** `sys/kern/sys_pdnew.c:472-473` / `509-510` — **`CAP_PDKILL` confused deputy.** pdsetfd/pdstart authorize on `CAP_PDKILL` alone, with no creator/credential check (`procdesc_find` resolves any holder's fd). The embryo runs the creator's (possibly root/set-id) creds. A privileged creator delegating the procdesc (SCM_RIGHTS) lets a lower-privileged holder inject fds into and schedule a foreign privileged process — strictly more authority than "kill". Contrast `sys_pdkill` (adds `p_cansignal`) and `pddupfd` (distinct right + `p_candebug`). Adjudicated high (correctness lens); reproduce lens rated medium (requires deliberate delegation). Consider dedicated `CAP_PDSETFD`/`CAP_PDSTART`, or refusing set-id via pdnew.

### Medium

- ✅ **[medium]** `sys/kern/sys_pdnew.c:330-369` — the interpreter re-entry loop never frees the previous iteration's `newtextdvp` (held dir-vnode vref), `newbinname` (M_PARGS), or namei pnbuf, unlike `do_execve` (`kern_exec.c:1152-1163`). Reachable via a 2-level chain (imgact_binmisc → `#!/bin/sh`); each such `pdnew()` leaks a vnode ref (blocks unmount) + kernel memory → DoS. Plain shebang can't nest, so this needs binmisc configured (common with qemu-user/linux binfmt).
- ✅ **[medium]** `sys/kern/kern_fork.c` `proc_destroy_embryonic` — **missing `pargs_drop(p->p_args)`.** On a successful `pdnew()` closed before `pdstart`, `exec_finalize` installed `p2->p_args` (refcount 1, local NULLed) but the destroy path frees `p_binname` and never drops `p_args`; normal reap does (`kern_exit.c:1090`). A `pdnew()`+`close` loop leaks M_PARGS unbounded → DoS. (Confirmed: zero `p_limco`/`process_exit`/`pargs_drop` in `kern_fork.c`.)
- ✅ **[medium]** `sys/kern/kern_exec.c:~1605` `exec_map_stack` — `kern_setrlimit(curthread, RLIMIT_STACK, …)` targets the **parent** on the pdnew path (`curthread` = caller, `imgp->proc` = embryo). A crafted `PT_GNU_STACK p_memsz` exceeding the current soft `RLIMIT_STACK` (but ≤ `rlim_max`, so no priv_check) silently raises the caller's stack rlimit and grows the caller's own stack region (the `P_INEXEC` guard in `setrlimit` is false because the parent isn't `P_INEXEC`), while the child's `rlim_cur` is never raised. `exec_map_stack` wasn't generalized for `imgp->proc != curproc`. Not corruption (parent-only growth, bounded by its own `rlim_max`) → medium.
- ✅ **[medium]** `sys/kern/sys_pdnew.c:290` — kern_pdnew fires `EVENTHANDLER_DIRECT_INVOKE(process_fork)` but `proc_destroy_embryonic` never fires `process_exit` (confirmed: absent from `kern_fork.c`; only `exit1` @`kern_exit.c:407` does). ## Gaps worth a follow-up pass

- **`process_exec` eventhandler + `proc:::exec-success` SDT never fire for a pdnew process — even on the SUCCESS path.** The review only flagged missing `process_exit` on the cancel path. But `exec_new_vmspace` (kern_exec.c, the new `if (vmspace != NULL) { … EVENTHANDLER_DIRECT_INVOKE(process_exec) … }` guard) skips `process_exec`, `itimers_exec`, and `sv_onexec_old` for the embryo because `p_vmspace==NULL`. Since that is the *only* site that fires `process_exec` during exec, a successfully spawned pdnew binary is invisible to hwpmc (`pmc_process_exec`), dtrace `proc:::exec`, and any tracer keying on it. Likewise `sys_pdnew` fires `SDT_PROBE1(proc,,,exec)` and `exec__failure` but never `exec__success`. This is a behavior/observability regression the review didn't consider, and it's in tension with the review's own suggested fix to "add process_exit" (see below).

- **`finstall_at()` (kern_descrip.c) was never examined on its own.** Two things: (a) its header comment states "the target table must not be concurrently accessed," yet pdsetfd and the shebang `/dev/fd/N` install call it on an embryo whose fd table is reachable through a closeable procdesc and through a second thread's concurrent `pdsetfd` — the contract is violated by the feature's own use, not just the UAF the review found; (b) the bound check `atfd >= getmaxfd(td)` uses the **caller's** `RLIMIT_NOFILE`, not the embryo's, so `EMFILE` is keyed to the wrong process.

- **`sys/vm/vm_map.c` (`vmspace_exec`) and `sys/kern/kern_resource.c` (`lim_rlimit` MPASS) changes are entirely unreviewed.** `vmspace_exec` now gates both `pmap_activate` *and* `TDP_EXECVMSPC` on `p==curthread->td_proc`; if `exec_new_vmspace` is ever driven a second time for one embryo across a word-size/ABI switch (shebang → interpreter), the first embryo vmspace is replaced with no reclaim (p≠curproc ⇒ no `TDP_EXECVMSPC`, no `post_execve` free) → vmspace leak. The `lim_rlimit` `MPASS(td==curthread || P_INEXEC)` relaxation is load-bearing for pdnew and its post-`pdstart` edge (assert would trip once `P_INEXEC` clears) wasn't validated.

- **Follow-on risk in the review's own recommended fixes (the "confirmed finding whose fix introduces a new one" category):**
  - *"Keep a `_PHOLD` across pdsetfd/pdstart/Phase 3"* is insufficient alone: `proc_destroy_embryonic()` (kern_fork.c:~1372) does **not** wait for `p_lock` to drain the way `exit1()` does, so a `_PHOLD` doesn't stop the free — the fix must also add a `p_lock` drain to `proc_destroy_embryonic`, or the UAF persists.
  - *"Add `process_exit` to `proc_destroy_embryonic`"*: `process_exit` handlers can deref `p->p_vmspace` (NULL if pdnew failed before `exec_new_vmspace`) and assume the process actually ran → a new NULL-deref/incorrect-teardown path.
  - *"Create the vmspace before `cpu_fork`"* (the fix for the i386/arm panic): this defeats every `vmspace != NULL` guard the commit added (in `exec_new_vmspace` and the `imgp->proc==curproc` fast paths), re-enabling `process_exec`/reuse logic on the embryo; those guards would all need re-auditing.

- **ABI/32-bit-host completeness stated but never confirmed.** The review's freebsd32 finding is only the 64-bit-parent / 32-bit-child case. Not addressed: the three syscalls are absent from the freebsd32 syscall table (`freebsd32/syscalls.master` is not in the diffstat), so a 32-bit process cannot call pdnew at all — worth stating as intentional vs. oversight. And on a native 32-bit/ILP32 kernel the same `imgp_suword`/`imgp_copyout` `long`-width paths run; worth a sanity pass.
